# v4.1.4 OCI 基线重建设计

## 背景

`upgrade/v4.1.3-oci` 是在旧 v4.1.1 系列代码上逐项迁移形成的候选分支。它没有以
官方 v4.1.3 发布提交为祖先，Console 还出现了 OpenPitrix 远程扩展的旧
`/apps-manage/repo` 路由覆盖本地路由的问题。该路径会渲染旧仓库页，因此丢失本项目已完成的
OCI 凭据、缓存、全量校验和同步摘要能力。

已验证的 `feature/oci-performance-cache` 在旧测试环境中可以正常渲染 OCI 仓库页，并包含完整
OCI 定制能力。因此本次不继续修补 `upgrade/v4.1.3-oci`，而是以该功能分支为基础，选择性吸收
官方 v4.1.3 的必要改动，形成项目自有的 v4.1.4 候选。

## 目标

1. 后端和 Console 都从同名 `feature/oci-performance-cache` 创建
   `upgrade/v4.1.4-oci`，保持前后端功能基线一致。
2. 吸收 v4.1.3 中与安全、应用生命周期、认证权限、Kubernetes 兼容性直接相关的改动。
3. 保留并优先使用当前分支的 OCI 实现；不以官方早期 OCI 实现覆盖缓存、凭据、异步同步和
   限流能力。
4. 最终发布的是本项目 Fork 的 `v4.1.4-mysstack.N`，不冒充上游版本。

## 非目标

- 不直接 `git merge v4.1.3`、不重写 `master`、不删除 `upgrade/v4.1.3-oci`。
- 不处理 Helm 4；运行时 Helm 3.22 的兼容性继续独立验证，不能借本次分支迁移臆测为已支持。
- 不迁移遥测端点、扩展市场内容或不影响本项目运行的上游改动，除非验证表明它们是构建前置条件。
- 不把 Console 原生 `/workspaces/:workspace/repos` 替换成新 UI；本项目的应用仓库页面仍由
  Appstore 的 `RepoManage` 承载，后续可单独做收敛。

## 基线与证据

| 组件 | 功能基线 | 官方参考 | 分叉点 | 差异 |
| --- | --- | --- | --- | --- |
| Backend | `feature/oci-performance-cache` (`6e80a4985`) | `v4.1.3` (`3ef3a6bc9`) | `e2f16d37b` | 功能线 215、上游 100 commits |
| Console | `feature/oci-performance-cache` (`4e2e21620`) | `origin/release-4.1` (`ee28f29f2`) | `5543000e3` | 功能线 135、上游 90 commits |

Console 没有独立 `v4.1.3` 标签；`release-4.1` 的 `ee28f29f2` 是与 Backend v4.1.3 同期的
官方维护参考。两者均只能作为补丁来源，不能作为整体合并来源。

Backend 直接三方合并的预估差异为 4,610 个文件、351,815 行新增、140,574 行删除，说明它会把
vendor、CRD 生成物、Chart 和定制 OCI 代码一起重放，无法形成可审查的迁移。因此采用
“提交归类 → 最小补丁吸收 → 每波测试”的方式。

## 迁移原则

1. 每个上游提交都归为 `采纳`、`按文件移植`、`当前实现优先` 或 `不采纳`，并记录原因。
2. 有当前实现的 OCI、手动同步、Repo 删除、TLS、Chart 下载、凭据和 Controller 并发逻辑时，
   先比较行为与测试；不能直接 cherry-pick 早期上游实现。
3. 依赖、CRD 和 Helm Chart 只在代码定稿后生成或更新，不能将旧生成物与新生成物混合。
4. 每个迁移波次提交一次，提交信息使用中文；每个波次均通过聚焦测试和 `git diff --check` 后再进入下一波。
5. 两仓库同名候选分支必须一起构建、部署和回归；任一端失败不合入 `master`。

特别处理：

- `7e703750e` 是官方的首版 OCI Repo 支持；当前分支已经在它之上扩展了缓存、tag 过滤、重试、
  私有凭据和异步同步，**不直接 cherry-pick**。仅从测试和 Registry 协议处理上提取当前缺口。
- `bb60d3943` 的手动同步与当前实现重叠，**不直接 cherry-pick**；只比对 CRD/OpenAPI 和 API
  兼容差异。
- `f29016726` 的 HTTPS TLS 修复、`92c004ada` 的删除流程可能与当前 Controller 同文件，按函数级
  移植并使用 HTTPS/OCI 双路径回归测试。
- `1952b98ca`、`12dec1558`、`3e936f991` 都包含依赖或 vendor 变动，不能分别 cherry-pick；以
  v4.1.3 最终 `go.mod` 为参考建立单一依赖升级提交。

## Console 迁移策略

Console 的 90 个官方提交按下面优先级选择：

1. 会话与路由：`cc6e1720e`、`20b7b8c58`、`57f98bc78`、`f4481c6ac`、`86324db86`、`649fd75ba`、
   `e20192408`。先确认不覆盖本项目已经验证的 401 自动登录跳转，重点回归刷新、服务重启和
   `/apps-manage/repo`/Workspace 应用仓库入口。
2. API 协议与权限：`9932e5d91`、`53db0d92`、`49377ea9f`，与 Backend 的服务账号/角色修复联合验证。
3. 运行时依赖与构建：`6e9ace360`、`0e2ff5a32` 等只在 Node 14 构建链可验证时吸收；不将 GitHub
   Action 使用的 Node 版本误当成 Dockerfile 运行时版本。
4. `chore(bot): update v3dist` 以及纯展示微调默认不采纳。OpenPitrix 远程扩展仍可能声明旧路由，
   因此不再向旧 `/apps-manage/repo` 添加兼容路由；测试入口以当前功能分支可正常工作的路径为准。

## 验收

- 两个 `upgrade/v4.1.4-oci` 分支都以对应 `feature/oci-performance-cache` 为直接父提交。
- Backend 的 OCI、HTTPS、Repo credential、Controller、KAPI 聚焦测试通过；Console 的类型检查、
  单元测试和生产镜像构建通过。
- 测试环境中应用仓库管理页能显示 OCI 凭据选择、验证、立即同步、全量校验和版本列表；重启
  `ks-apiserver` 后 401 自动回到登录页。
- OCI 私有仓库与公开 HTTPS Repo 都可验证、同步和部署；不输出密码或 Token。
- 最终镜像使用来源分支加日期和短 SHA 标签；候选测试通过后才创建项目自有 release 分支和标签。

## 回滚

`feature/oci-performance-cache`、`upgrade/v4.1.3-oci` 和远端同名分支永久保留。新分支每个波次
都是可逆提交；出现功能、构建或测试环境回归时回退该波次，不回写、不强推既有分支。
